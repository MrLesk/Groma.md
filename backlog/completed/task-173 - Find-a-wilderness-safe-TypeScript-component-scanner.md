## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
When a developer scans an unfamiliar TypeScript repository, Groma should produce the most plausible component map it can from native project evidence without requiring Groma-specific source conventions. Compare playground scanner strategies on Groma, Backlog.md, and codex-hackathons, using independent cold reviews before and after each trial, then recommend the strategy most likely to survive wild TypeScript projects. Production scanner changes are outside this spike.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Freeze exact scanner-readable copies of Groma, Backlog.md, and codex-hackathons with hashes for the corpus, expectations, runner, scorer, runtime, lockfile, and each strategy closure.
2. Run the conservative control and exclusive-private-callee strategy five times per repository through one runner, recording raw observations, stability, grouping, fragmentation, sampled false merges, coverage, and repository-specific resolution limits.
3. Use fresh GPT-5.6 xhigh reviews before and after each executed trial plus fresh Grok 4.6 xhigh post-run reviews; audit every grouped component rather than trusting the small expectation sample.
4. Reject exclusive private-callee grouping because import ownership and fixpoint absorption create semantically mixed components; stop the proposed pure-facade trial because the frozen candidates contain no qualifying positive pair.
5. Select conservative file-level scanner evidence as the safest tested strategy. Recommend complete batch reconciliation where architecture Markdown preserves curated multi-file ownership and unknown files begin as singleton proposals.
6. Retain one concise conclusion and one deterministic self-contained archive containing the executable harness, frozen corpora, 30 raw runs, reports, audits, expectations, rejected strategies, and six review records.
